# @motored-stellar/claims

The off-chain half of the delivery-claim system (pre-award, not billed; used by SCF deliverable **D6**: delivery
claims anchored in a registry, the anchoring job and the public re-check library).

When the carrier reports an order's parcel delivered, the operator adds a delivery
claim to a batch. Every hour the batch's Merkle root is written to the claim
registry (`contracts/claim-registry`) with `anchor(batch_id, root)`. The escrow
guard (`contracts/guard`) later checks a claim's Merkle proof against that root
before it lets a seller be paid without the buyer's approval.

## What is in here

| Module | What it does |
|---|---|
| `src/leaf.ts` | The claim leaf, byte for byte as the guard's `leaf()` builds it, plus the salted HMAC parcel commitment and the carrier event reference |
| `src/merkle.ts` | Padded SHA-256 Merkle batches (`0x02` nodes, `0x03` padding leaves), proofs, and a local mirror of the registry's `verify` |
| `src/anchoring.ts` | `ClaimAnchoringJob`: delivered events in, one claim per escrow, hourly batch, `anchor`, proofs stored per claim |
| `src/recheck.ts` | Public re-check of a released order's claim (used by `scripts/claims/recheck.ts`) |
| `src/registry-soroban.ts` | `SorobanRegistryClient` (reads by simulation, writes through the Signer and Submitter ports) and `RpcSubmitter` |
| `src/ttl.ts` | Ledger keys and `ExtendFootprintTTL` transactions for the registry, guard registrations, open escrows, their asset balance entries and Wasm code |
| `src/scval.ts` | The guard's `Claim` as an ScVal, and the public claim bundle JSON |
| `src/ports.ts`, `src/memory.ts` | Ports and their in-memory implementations |

## Leaf format

```
leaf              = sha256(0x01 || XDR(ScVal::Address(escrow)) || order_ref || parcels_commit
                           || carrier_event_ref || u64_be(delivered_at))
order_ref         = 32 random bytes per order (never a database id)
parcels_commit    = HMAC-SHA256(per-order secret salt, UTF-8 parcel number)
carrier_event_ref = sha256(parcel number || status text || dateTime || "lang=en")   (UTF-8, no separators)
node              = sha256(0x02 || left || right), index bits lowest first say "running hash is the right child"
padding leaf i    = sha256(0x03 || u32_be(i))   (batches are padded to a power of two)
```

The registry walks a proof of at most 32 siblings and requires the index to be fully
consumed, so a batch padded to a power of two gives every real leaf a proof it accepts
unchanged. Tag `0x00` is reserved for field-level leaves of other record formats and is
never a delivery claim.

No directly identifying data goes on-chain: the order reference is random and the
parcel number is only present as a salted HMAC, so it cannot be enumerated and linked
to the carrier's public tracking page. Salts stay in the operator's `SaltStore`.

## Ports

| Port | Purpose | In-memory implementation |
|---|---|---|
| `DeliveryOracle` | Delivered events from the operator's carrier integration (escrow, order ref, parcel number, carrier status text and time, delivered_at) | `InMemoryDeliveryOracle` |
| `RegistryClient` | `anchor`, `verify`, `anchoredAt`, `revoke` | `InMemoryRegistry` (contract semantics, no auth) / `SorobanRegistryClient` |
| `SaltStore` | Per-order secret salts | `InMemorySaltStore` |
| `ClaimStore` | Pending and anchored claims, batch ids, oracle cursor | `InMemoryClaimStore` |
| `Signer`, `Submitter`, `Clock` | Same roles as in `@motored-stellar/escrow` (declared structurally here) | `ManualClock`, `RpcSubmitter` |

The carrier's tracking client is not part of this repository. It belongs to the
operator's own system and feeds `DeliveryOracle`; it decides which statuses count as
delivered and emits only events whose timestamp parsed.

## Use

```ts
import {
  ClaimAnchoringJob, InMemoryClaimStore, InMemoryDeliveryOracle, InMemoryRegistry,
  InMemorySaltStore, ManualClock, recheckClaim,
} from "@motored-stellar/claims";

const clock = new ManualClock();
const registry = new InMemoryRegistry(clock); // or new SorobanRegistryClient({...})
const job = new ClaimAnchoringJob({
  oracle: new InMemoryDeliveryOracle(), salts: new InMemorySaltStore(),
  registry, store: new InMemoryClaimStore(), clock,
});
await job.ingest();                 // as events arrive
const batch = await job.anchorBatch(); // hourly
const claim = await job.claimFor(escrowId); // goes into the guard's ResolveSeller signature
const check = await recheckClaim(registry, escrowId, claim!);
```

## Test

```bash
npm test -w @motored-stellar/claims        # vitest
cargo test -p motored-escrow-guard test_vectors   # the Rust side of the golden vectors
```

`test/vectors.json` is generated by `test/gen-vectors.mjs` with `node:crypto` only (no
Stellar SDK) and asserted both here and in `contracts/guard/src/test_vectors.rs`
against the contract's own `leaf()`. If either side changes, both tests fail.

Testnet only. Nothing in this package holds or prints a secret key; writes are signed
through the `Signer` port.
